# Shell federated app — starter kit

Public Module Federation **remote** template for Groundfloor Shell apps.
Download this folder (or the ZIP from Customer Portal → Apps → your Shell app),
match it to your Portal app, build, and publish `release.zip`.

You do **not** need access to the private Shell monorepo.

## Instructions for agents

Read this section before creating anything on Groundfloor.

0. **Enable `@groundfloorcloud/mcp`.** This kit ships `.mcp.json` (`npx -y
   @groundfloorcloud/mcp`). Cursor on macOS: copy `.cursor/mcp.json.example`
   (do not use `npx`). Do not use `@groundfloor/coderunner-mcp`. A human must
   `gf login` first. Then `docs_get` id `shell`.
1. **Obtain this kit with `gf apps init`.** Never invent `src/App.tsx`,
   `vite.config.ts`, or a Module Federation remote from memory.
   `BrowserRouter` belongs only in `src/dev/DevShell.tsx`. Wrapping `App` in a
   router crashes the production Shell (`RemoteErrorBoundary`).
2. **This folder is a Shell UI remote, not a Coderunner workload.**
   - Flow: `gf apps init --slug <slug>` → `gf apps create` (once) →
     `npm run release` → `gf apps publish`.
   - Do **not** run `gf deploy` on this folder.
   - Do **not** `POST /v1/workspaces/{id}/apps` with `app_kind=coderunner` (rejected).
3. **Auth:** a human must run `gf login` once. Then use `eval "$(gf env)"` or
   `GROUNDFLOOR_TOKEN=$(gf token)`. You cannot complete browser login by yourself.
4. **Workspace:** `gf workspaces` then `gf workspaces use <uuid>`.
5. **Register (if the Portal app does not exist yet):**

```bash
gf apps create --name "My Federated App" --slug my-federated-app \
  --kind shell_federated --manifest ./groundfloor.manifest.json
```

6. **Match ids:** `gf apps init --slug <portal-slug>` sets
   `groundfloor.manifest.json` → `appId` and `src/appIdentity.ts` → `APP_ID`.
   Keep them equal to the Portal **slug**.
7. **Build + publish:**

```bash
npm install
npm run release
gf apps publish --path release.zip
```

   `gf apps publish` reads `appId` from `groundfloor.manifest.json` when you omit
   the app argument. It uploads `release.zip` from `npm run release` (do not zip
   Vite `dist/` yourself). Publish flattens an `assets/` layout if you do, and
   rewrites `./assets/` imports in `remoteEntry.js` so sibling chunks resolve
   after flatten. The official kit already does both.

Hosts: Control Plane `https://platform.groundfloor.cloud`, Portal
`https://app.groundfloor.cloud`, docs
https://docs.groundfloor.cloud/docs/developer-tools/ai-agents

If the user asked to deploy a **function / job / schedule / service**, stop and
use `gf deploy` in a workload project — not this kit.

Visual rules: [Design standard](https://docs.groundfloor.cloud/docs/apps/shell/styling). MCP `docs_get` id `design-standard`.

Own CSS framework (Bootstrap, MUI, …): do not load it globally. Use `FederatedStyleRoot` (Shadow DOM). [CSS and styling](https://docs.groundfloor.cloud/docs/apps/shell/styling). MCP `docs_get` id `css-and-styling`.

Data: Dataplane is not a database. You have PostgreSQL ready through Dataplane (shared, platform-managed, no deploy step). Deploy a dedicated Postgres if you want your own instance, then use it through Dataplane or on your own. MCP `docs_get` id `databases`.

## Quick start

```bash
# From the unzipped folder
npm install

# Sign in once (CLI session lives in ~/.groundfloor)
gf login

# Standalone preview (mock Shell chrome) — http://localhost:4175
# Uses `gf login` when a CLI session exists; otherwise sample vault fixtures.
npm run dev

# Force sample data even when logged in
npm run dev:fixtures

# Build + pack for Portal publish
npm run release
# → release.zip  (remoteEntry.js at zip root — required)
```

Publish:

```bash
gf login
gf workspaces use <workspace-uuid>
gf apps publish --path release.zip
```

Or upload `release.zip` in **Customer Portal → workspace → Apps → your app → Releases**.

### About `remoteEntry.js`

This file is **generated by the build** (`vite` + Module Federation). It is not in the ZIP sources and you should not write it yourself.

- After `npm run build`: `dist/assets/remoteEntry.js`
- After `npm run release`: also `release/remoteEntry.js` inside `release.zip` (upload that zip)

It is bundled JavaScript that tells the Shell host how to load your exposed `./App`. Edit `src/App.tsx` instead; rebuild to refresh `remoteEntry.js`.

## Match your Portal app

1. In Portal, open your Shell app and note the **slug** (and manifest `appId`, usually the same).
2. Set the same id in:
   - `groundfloor.manifest.json` → `appId`
   - `src/appIdentity.ts` → `APP_ID`
3. Align `routes[]` in the manifest with pages under `src/App.tsx`.
   Paths are segments (`home`, `records`), never `/home`. In-app links must use
   `useAppPath('records')` — never `to="/records"`.
4. Keep Portal’s manifest in sync: `gf apps publish` does this from
   `groundfloor.manifest.json`, or paste the same JSON in Portal.

Federation remote `name` is derived as `appId` with non-alphanumerics → `_`
(e.g. `my-federated-app` → `my_federated_app`). Do not change that rule.

## Local Shell host (optional)

If you run a Shell host against an unpublished remote:

```bash
SHELL_REMOTE_DEV_URL=http://localhost:4175/assets/remoteEntry.js
# after `npm run release` + `npm run preview:release`:
# SHELL_REMOTE_DEV_URL=http://localhost:4175/remoteEntry.js
```

## Layout

```text
├── AGENTS.md                   ← MCP first, then routing + CSS rules
├── .mcp.json                   ← npx @groundfloorcloud/mcp (Claude Code / generic)
├── .cursor/mcp.json            ← same npx default; macOS Cursor: use mcp.json.example
├── groundfloor.manifest.json   ← Portal contract (appId, routes, theme)
├── vite.config.ts              ← Module Federation remote + gf token proxy (dev)
├── vite/gfControlPlaneProxy.ts ← `gf token` on /control-plane (dev only)
├── tailwind.config.js          ← scoped to .gf-federated-app; preflight off
├── scripts/prepare-release.mjs ← flattens dist → release.zip
├── .cursor/rules/              ← federated routing, CSS, databases
├── src/App.tsx                 ← exposed ./App for Shell
├── src/appIdentity.ts          ← APP_ID (keep in sync with manifest appId)
├── src/index.css               ← Tailwind (shared contract with Shell)
├── src/lib/useAppPath.ts       ← /apps/{slug} href helper
└── src/dev/                    ← standalone Dev Shell at /apps/:slug/* (not in federation build)
```

## Routing and CSS

1. **In-app links use `useAppPath`** — never `to="/page"`. Shell URL is `/apps/{slug}/page`. See `src/lib/useAppPath.ts`.
2. **CSS matches Shell Tailwind** — import `src/index.css`, wrap with `FederatedAppRoot`, keep remote preflight off. Other frameworks: `FederatedStyleRoot` + Shadow DOM (`docs/css-and-styling.md`).
